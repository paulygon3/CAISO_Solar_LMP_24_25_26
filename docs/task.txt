# Codex Task: Build CAISO-Wide Hourly Zonal Solar-Weighted LMP Excel Workbooks, 2024–2026

## Objective

Develop and execute a complete, reproducible Python pipeline that:

1. Downloads actual published CAISO hourly day-ahead LMP data for every available published pricing location.
2. Builds three standardized hourly solar-production profiles: NP15, ZP26, and SP15.
3. Maps pricing nodes to the appropriate solar zone using documented evidence.
4. Calculates zonal solar-weighted nodal prices, monthly and annual summaries, matched-period comparisons, and basis to all three trading hubs.
5. Produces exactly three final Excel workbooks:

- `CAISO_Solar_Weighted_LMP_2024.xlsx` — January 1 through December 31, 2024.
- `CAISO_Solar_Weighted_LMP_2025.xlsx` — January 1 through December 31, 2025.
- `CAISO_Solar_Weighted_LMP_2026.xlsx` — January 1 through November 18, 2026, inclusive.

This is an implementation and data-delivery task, not a research summary or prototype. Complete the downloads, processing, validation, and workbook creation. Do not stop after writing code.

Never fabricate prices, interpolate missing LMPs, replace missing prices with zero, or substitute simulated prices.

If credentials, network restrictions, source availability, runtime, storage, or other constraints prevent completion, identify the exact blocker, preserve resumable progress, and state what remains. Do not claim execution or completeness that has not been established.

## 6. Standardized zonal solar-production profiles

The primary scenario uses three fixed TMY-based modeled profiles, not actual-year generation.

The goal is:

- Consistent solar assumptions within each zone.
- Consistent zone-specific assumptions across years.
- Real differences in modeled production timing between zones.

### Profile construction

Develop a representative profile separately for NP15, ZP26, and SP15.

Prefer a documented multi-location composite where practical.

1. Identify suitable solar-model locations.
2. Support their zonal placement with official geographic or zone evidence where obtainable.

4. Document reference coordinates and returned weather-grid/station locations.

6. Define the location weights.
7. Keep the locations, weights, resource, and model configuration fixed across the three years.

If authoritative installed-capacity weights are readily available and suitable, they may be used.

Otherwise, use an explicitly labeled standardized alternative, such as an equal-capacity composite of documented representative locations. Do not invent installed-capacity weights or describe an equal-weight composite as actual fleet output.

Use a small, defensible set of locations rather than creating an open-ended geographic research project. Document representativeness limitations.

If defensible zonal placement or profile construction cannot be established, identify the blocker. Do not silently revert to one Fresno profile.

### PV system assumptions

Apply the same utility-scale configuration at every modeled location:

| Parameter | Requirement |
|---|---|
| Equivalent AC capacity | 100 MW |
| Equivalent DC capacity | 130 MW |
| DC/AC ratio | 1.30 |
| Technology | Utility-scale PV |
| Tracking | One-axis with backtracking |
| Module | Standard |
| System losses | 14% |
| Ground coverage ratio | 0.40 |
| Curtailment | Excluded |
| Battery storage | Excluded |

Verify PVWatts API parameters and units before execution.

Expected configuration, subject to documentation verification:

- `system_capacity = 130000` kW DC.
- `dc_ac_ratio = 1.30`.
- One-axis tracking with backtracking.
- Standard module.
- `losses = 14`.
- `gcr = 0.40`.
- Hourly output.
- NSRDB TMY resource.
- Explicit tracking-axis tilt and azimuth assumptions.
- Explicit inverter efficiency and material defaults.

Use a horizontal north–south tracking axis unless a documented modeling requirement supports a different configuration.

PVWatts hourly `ac` output is expected in watts; verify against current documentation and convert consistently:

`solar_output_mw = ac_watts / 1_000_000`

`normalized_output = solar_output_mw / 100`

For zone `z`:

`zonal_solar_weight_z,t = sum(location_weight_k × normalized_output_k,t)`

Require location weights within each zone to sum to one.

The equivalent zonal output is:

`zonal_output_mw_z,t = zonal_solar_weight_z,t × 100`

For aggregation:

`weight_hours_z,t = zonal_solar_weight_z,t × interval_duration_hours`

For hourly records, weight-hours are numerically equal to the normalized weight.

Validate negative, nonfinite, or unexpectedly high output. Do not silently clip unexpected values to force an expected range. Preserve originals and document any correction.

## 9. Core zonal solar-weighted LMP calculation

For node `i`, timestamp `t`, and its applicable assigned zone `z(i,t)`:

`node_weight_hours_i,t = zonal_solar_weight_z(i,t),t × interval_duration_hours_t`

For a requested period `P`, define:

- Expected pricing hours.
- Hours with valid node prices.
- Hours with a valid applicable zonal weight.
- Matched valid node-price/weight hours.

Calculate:

`weighted_lmp_numerator_i,P = sum(LMP_i,t × node_weight_hours_i,t)` over matched valid hours.

`matched_weight_hours_i,P = sum(node_weight_hours_i,t)` over matched valid hours.

`solar_weighted_lmp_usd_per_mwh = weighted_lmp_numerator / matched_weight_hours`

If the denominator is zero, return blank with a reason.

### Full-period solar denominator

For a completely mapped node:

`full_period_weight_hours_i,P = sum(applicable node-zone weight_hours over all expected hours)`

`solar_coverage_pct = 100 × matched_weight_hours / full_period_weight_hours`

Do not shrink the denominator to observed pricing dates.

If mapping or solar-profile gaps prevent a valid full-period denominator:

- Leave full-period solar coverage and the primary assigned-zone estimate unreported.
- Flag the mapping/profile problem.
- Do not disguise it as ordinary price missingness.

### Hour coverage

`hour_coverage_pct = 100 × valid_price_duration / expected_period_duration`

Hour coverage can be calculated even when zone mapping is unresolved.

For hourly inputs, report expected hours and valid-price hours explicitly.

### Missing and zero values

- Missing prices are excluded from the weighted numerator and matched denominator.
- Missing prices are never zero-filled.
- Valid zero and negative prices remain valid.
- A valid price during a zero-output hour contributes zero to the weighted numerator.
- A missing price remains blank in both raw and weighted matrices, including at night.

## 13. Hub basis to SP15, NP15, and ZP26

For each node and each hub:

`basis_i,h,t = node_lmp_i,t − hub_lmp_h,t`

Use matched timestamps where node price, hub price, and the node’s assigned zonal weight are valid.

Calculate:

`solar_weighted_basis_i,h = sum(basis_i,h,t × node_weight_hours_i,t) / sum(matched_pair_node_weight_hours_i,h)`

The node’s assigned zonal profile must weight both sides of the comparison.

Retain:

- Matched hours.
- Pairwise hour coverage.
- Pairwise solar coverage.
- Pairwise weighted numerator.
- Pairwise weight denominator.
- Matched-support node weighted price.
- Matched-support hub weighted price.
- Retained basis estimate.
- Display-facing basis estimate.
- Eligibility and reason.

Verify:

`matched_node_weighted_price − matched_hub_weighted_price = solar_weighted_basis`

Do not subtract a node’s own-zone summary from a hub summary calculated using a different zone’s profile and call it matched basis.

For standalone hub summaries:

- NP15 uses NP15 production.
- ZP26 uses ZP26 production.
- SP15 uses SP15 production.

Label standalone hub results separately from hub prices recalculated under a node’s profile for basis.

Use the 90% pairwise solar-coverage threshold for display-facing basis, retaining calculable lower-coverage estimates separately.

## 19. Mandatory calculation QA

Verify:

- Canonical keys are unique after documented revision handling.
- Joins do not lose or multiply price records.
- Every expected hour is represented.
- Same-zone nodes use the same profile at each timestamp.
- Different zonal profiles remain distinct where modeled output differs.
- Identical nighttime weights are not treated as an error.
- Every node uses its applicable assigned-zone profile.
- Unresolved mappings receive no silent fallback.
- Solar units are correct.
- DST and leap-day mapping are correct for each profile.
- Missing prices remain missing.
- Negative prices and contributions remain.
- Valid zero-output observations contribute zero.
- Normalized solar shares sum to one when the denominator is positive.
- Normalized price contributions sum to SWLMP.
- Negative exposure lies within `[0,1]`.
- Coverage lies within `[0,100]`, subject to numerical tolerance.
- Matched weight does not exceed full-period weight.
- Matched basis identities reconcile.
- Missing components are not treated as zero.
- Component checks use verified definitions.
- Annual/matched-period results reconcile.
- Heatmap rules hold.
- Reference rows are distinguishable.
- 2026 stops at the requested delivery date.

Do not use assumed solar-peak timing or price-trough timing as conclusive proof of correctness. Timing shapes may be diagnostic, but documented timestamp alignment is the primary test.

Do not automatically reject extreme published prices. Preserve, flag, and verify them.
